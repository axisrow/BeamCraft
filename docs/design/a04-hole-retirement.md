# A04 hole removal and monotone identity history

`remove-hole --store ROOT --id PLATE_UUID --operation-id RECORD_UUID` uses a new
logical `--op-id` and the common revision/actor/project/workspace options. Model
`RemoveHole`, engine `remove_hole` and adapter `RemoveHoleRequest` remove one
explicit owned record and replay the whole P11 definition group in one revision.
Legacy create-authored holes are not addressed by positional indices. Undo/redo
restores the complete earlier authored and derived state.

The A03 bounded history implementation is shared with holes. New optional USD
fields `steel:hole:nextOrdinal` (int 0..1000) and `steel:hole:retiredOperationIds`
(sorted unique UUIDv7 string[], at most 1000) prevent record/semantic cap reuse
on the current branch of model history. The first history-capacity scope is 1000
lifetime hole ordinals, with at most the existing 64 live holes. Exhaustion is an
explicit limit, never recycling or silent coarsening. Cross-kind cut/hole UUIDs
remain unique, including retired records and records generated by independent copies.

Shared counters live on the canonical P11 owner; dependent meshes update together.
Independent copies receive new record UUIDs and do not inherit irrelevant retired
identities. Empty hole replacement authors four typed empty arrays to mask weaker
owned layers. Fresh unholed elements still author no hole attributes. Counters are
read from composed opinions and cannot regress through ordinary command authoring.

The codeless schema descriptor/pin changes. Unsupported old pins fail explicitly;
no automatic migration or rewrite is performed. Foreign/future-schema content stays
inert. Capture, footprints and rebase classify history as shape-input metadata;
body shape and quantity signatures include only the actual live operations.

Immutable removal evidence returns the original post-removal revision/result on a
retry after later edits or deletion. Matching add-hole retries still return their
original accepted result without reactivating a retired record. A new cut or a new
creation request cannot reuse a retired UUID. No live ordinal is invented in removal
responses. The append engine also checks ordinal arithmetic instead of overflowing
on an untrusted `usize::MAX` record.

Original CLI/native/engine regressions cover middle/last removal, ordinal gaps,
linked undo/redo, copied UUIDs, cross-kind collisions, repeated requests, unchanged
heads on refusal, exhausted counters, weaker-layer masking and large-ordinal input.
